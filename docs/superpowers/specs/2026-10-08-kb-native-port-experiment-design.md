# kb native port experiment — design

- **Date:** 2026-10-08
- **Status:** approved design, awaiting implementation plan
- **Track:** platform (experiment); the Raycast repo is read, never written
- **Reference implementation:** `~/Work/raycast/kb` — `packages/domain/kb` and `apps/kb/src/search.screen.tsx`

## Goal

Decide, with numbers, whether a native Rust port of kb's search command — built on GPUI Kit and free of Raycast's
extension size and runtime limits — is worth having. The experiment:

1. measures the current Raycast implementation;
2. builds an MVP port with the same UI/UX, in Rust on `gpui-kit`, that is maintainable, fast, efficient and small;
3. renders the same notes — identical Markdown, with formatting and syntax highlighting intact;
4. measures the port the same way;
5. publishes a report comparing performance, maintainability and adherence to best practices.

The port follows three skills as normative guides: `~/.agents/skills/gpui-kit` (including its Coding Guides),
`~/.agents/skills/gpui-kit-design-guides`, and `~/.agents/skills/rust-best-practices`.

## Decisions

| #   | Question                 | Decision                                                                                                                                                     |
| --- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | MVP scope                | Core loop: list, FTS search, split pane with rendered notes, detail screen, type and tag filter, primary and copy actions, manual sync with its report.      |
| D2  | Measurement depth        | All three tiers: engine benchmarks, process footprint, perceived end-to-end latency.                                                                         |
| D3  | Launch model             | Resident launcher: background app, global hotkey, floating panel, hidden on Esc or blur.                                                                     |
| D4  | Notes rendering          | GPUI Kit `TextView` (Markdown) with a tree-sitter `code_block_highlighter`; mermaid rendered natively and offline with `merman`.                              |
| D5  | Project shape            | Cargo workspace mirroring kb's layering: a pure domain crate, an app crate, a bench crate, an `xtask`.                                                       |
| D6  | Location and tooling     | New repo `~/Work/rust/kb`, bootstrapped like kb: mise for tools and tasks, hk for hooks, `kb/hk.pkl` ported step by step, kb-shaped documentation.          |

## Scope

**In:** everything `search.screen.tsx` does day to day, plus sync and its report:

- search bar with FTS5 prefix search, ranked results, pages of 50;
- list rows with icon (favicon for bookmarks), title, subtitle and accessories (tags);
- type and tag multi-select filter (any selected type, every selected tag);
- split pane showing the entry's notes and metadata; toggled with ←/→;
- pushed detail screen;
- action palette (⌘K): primary action, copy URL / title / description / notes / raw YAML, open source file, links
  submenu, rebuild index, preferences;
- empty states; manual sync with progress, cancellation and a per-file report.

**Out:** jobx (capture, opportunities, fill), yabai, Windows and Linux, signing and publishing, any write to the
Raycast repo.

## Architecture

### `kb-domain`

A synchronous library with no UI dependency, one module per TS file in `packages/domain/kb/src`:

| Module     | TS counterpart | Responsibility                                                                                 |
| ---------- | -------------- | ---------------------------------------------------------------------------------------------- |
| `entry`    | `entry.ts`     | `Entry`, `EntryLink`, id derivation, primary content, link and tag normalization               |
| `type`     | `type.ts`      | known entry types, labels, type extraction                                                     |
| `source`   | `source.ts`    | recursive `.yml`/`.yaml` discovery, parsing, skipped entries                                   |
| `markdown` | `markdown.ts`  | `build_entry_markdown`, byte-compatible with the json2md output                                |
| `row`      | `row.ts`       | `IndexRow`, searchable notes text, entry ↔ row                                                  |
| `sync`     | `sync.ts`      | the same `SCHEMA_DDL`; transactional, cancellable (`AtomicBool`), progress callback             |
| `query`    | `query.ts`     | sanitize, tokenize, FTS5 prefix query                                                          |
| `search`   | `search.ts`    | `FilterState`, `SearchQuery`, `build_search_sql`, `PAGE_SIZE = 50`                              |
| `report`   | `report.ts`    | per-file sync report and source excerpts                                                       |

Dependencies: `serde`, a YAML parser that keeps key order (`serde_yaml_ng` or `saphyr`, chosen in the plan by the
golden tests), `rusqlite` (`bundled`, FTS5), `walkdir`, `thiserror`. Errors are typed enums; the library does not
panic, print or exit. `#![warn(missing_docs)]`.

The index keeps the Raycast schema — `entries`, `entries_fts` (FTS5 over title, description, notes),
`entry_tags` — so query semantics and ranking can be compared. It lives at
`~/Library/Application Support/kb-native/kb.db` and never touches Raycast's.

### `kb-app`

| Unit       | Built from                                                                    | Owns                                                                          |
| ---------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `main`     | GPUI app, `global-hotkey`, a pop-up window kind, no Dock icon                  | lifecycle; hotkey → show/reuse panel; hide on Esc/blur                        |
| `search/`  | `List` + `ListDelegate`, `Input`, `ListItem`, `Icon`, `Label`, `Tag`, `img()` | `SearchView` entity: query, results page, selection, detail toggle            |
| `filter`   | `Popover` + `Command` (grouped, searchable, checkmarks)                        | type and tag multi-select                                                     |
| `detail/`  | `Resizable` split, `TextView::markdown`, `DescriptionList`, `Tag`, `Link`      | notes rendering, highlighter, mermaid plugin, one shared metadata view        |
| `nav`      | `NavStack`                                                                    | detail and sync screens pushed over search; Esc pops                          |
| `actions`  | `Command` in a `Popover`, typed GPUI `Action`s, `KeyBinding`, `Kbd`            | ⌘K palette; shortcut hints from bindings, never hand-written strings          |
| `sync/`    | `List` with sections, `Progress`, `Spinner`, `Notification`, `DescriptionList` | sync run, cancellation, report                                                |
| `empty`    | `Empty`                                                                       | no index / no results states                                                  |
| `config`   | TOML file `~/.config/kb/config.toml`                                          | `sources_path`, default `~/.config/kodexb/sources`; hotkey                     |

Highlighting: `TextView::code_block_highlighter` backed by the GPUI Kit tree-sitter highlighter, with the grammar
features the notes actually use: bash (also `sh`, `zsh`), python, ruby, yaml, javascript (`js`, `jsx`),
typescript (`ts`, `tsx`), sql, json, toml, markdown (`md`), kotlin. Unknown languages render unhighlighted.

Mermaid: a `TextView` block plugin renders ` ```mermaid ` blocks with `merman`, offline. The TS side renders them
as remote `mermaid.ink` images; this is a deliberate improvement, and its binary-size cost is reported separately.
The Markdown string still matches the TS output byte for byte; only the renderer differs.

State ownership follows the GPUI Kit Coding Guides: retained state in `Entity<T>`, stateless parts as
`RenderOnce`, stable `ElementId`s, subscriptions stored on the view that observes.

### Data flow

1. A keystroke updates the query; it is debounced by 150 ms, the TS side's `DEBOUNCE_MS`.
2. A background task runs `kb_domain::search` on a read-only connection.
3. The page replaces the delegate's items; the view notifies and re-renders.
4. Selecting a row renders its pre-compiled notes Markdown in `TextView`.
5. Sync runs on the background executor and streams progress events to the sync view; cancelling sets the flag and
   the transaction rolls back.

## Measurement

Every result records machine, OS, power state, toolchain and app versions, and is written as JSON in one shared
schema under `docs/experiment/results/`.

**Corpus.** `fixtures/sources/` (69 files, 2.8 MB) and `fixtures/sources-10x/`, generated by `xtask fixtures
--scale 10` by duplicating files with renamed keys.

**Tier 1: engine.** The same cases on both sides: scan and parse; full sync, cold and warm; `build_entry_markdown`
over every entry; search latency p50/p95/p99 over 30 fixed queries (empty, one to three words, prefixes, with and
without type and tag filters). Rust: `criterion` in `kb-bench`. TS: `bench/ts/bench.ts` under Node (what Raycast
runs: Node 22) and under Bun (reference only).

**Tier 2: footprint.** RSS of the Raycast extension's Node worker vs `kb-app`: idle with the panel hidden, panel
open, and after 100 scripted queries. Cold-start CPU time. Artifact size: built extension plus runtime
`node_modules` vs the stripped release `.app`, with mermaid and the grammars broken out by `cargo bloat`.

**Tier 3: perceived latency.** Hotkey → first frame and keystroke → updated list. `kb-app --trace` logs monotonic
timestamps. A shared harness (`osascript` driving the hotkey and keystrokes, 120 fps screen recording, frames
counted with `ffmpeg` scene detection) runs against both apps and cross-checks the self-reported numbers. Median
and IQR over 30 runs, with stated error bars. Both apps debounce by 150 ms, so keystroke latency is reported
with the debounce included and, for `kb-app`, also from debounce settle to paint.

`mise run bench` runs tiers 1 and 2; `mise run bench:e2e` runs tier 3, which is semi-manual.

## Parity and testing

- **Goldens.** `xtask goldens` runs the TS domain over the fixtures and writes, per entry, the `IndexRow` JSON and
  the notes Markdown, and, per query, the ordered ids. Rust asserts byte equality for Markdown and rows and the same
  id order for queries; ties in FTS rank break by id on both sides. Goldens are regenerated deliberately and
  committed.
- **Unit tests** beside the code (`#[cfg(test)]`); `proptest` for query sanitizing and tokenizing.
- **UI tests** with GPUI's `TestAppContext`: search → select → detail; filter toggling; ⌘K actions; sync cancel.
- **Visual check.** Side-by-side screenshots of ten representative entries: code-heavy, tables, mermaid,
  bookmarks, tasks.

### UI/UX parity

`docs/experiment/parity.md` is the UI/UX parity matrix. It is written before the UI is built, from the Raycast
command's code (`search.screen.tsx`, `features/kb/*`, `features/kb/sync/*`), and holds one row per user-visible
behavior: surfaces (list row, accessories, split pane, metadata, detail screen, empty states, sync progress and
report), every action and its shortcut, the filter, navigation (←/→, Esc, ⌘K, push and pop), and copy.

Each row records a status, the evidence for it, and, unless the status is **Same**, a justification:

| Status      | Meaning                                                                        | Justification required |
| ----------- | ------------------------------------------------------------------------------ | ---------------------- |
| **Same**    | Behaves and reads as in Raycast                                                | no                     |
| **Adapted** | Works differently because GPUI Kit, the Design Guides or the platform differ  | yes                    |
| **Better**  | Goes beyond Raycast (for example a resizable split, offline mermaid)           | yes                    |
| **Missing** | Not delivered                                                                  | yes, with a follow-up  |

Evidence for each row is a `TestAppContext` test, a screenshot pair, or both. Two measures come from the
matrix:

- **Coverage:** the share of rows that are Same, Adapted or Better.
- **Task cost:** for five scripted tasks — find and open a bookmark, copy a command, filter by a type and a tag,
  read a code-heavy note, rebuild the index — the keystrokes needed and the tier-3 time to finish, on both apps.

## Report

`xtask report` turns the results JSON into `docs/experiment/report.md`:

1. Performance: tiers 1–3, tables and charts.
2. Footprint and size.
3. Maintainability: lines of code; dependency count and depth (`cargo tree` vs the npm lockfile); cold and
   incremental build time; test count and coverage; clippy, jscpd and complexity findings vs fallow's health.
4. Best-practice adherence: checklists from the rust-best-practices chapters and the GPUI Kit Coding and Design
   Guides, each item scored with file references.
5. Parity: golden results, and the UI/UX parity matrix with coverage, task cost, and every Adapted, Better and
   Missing row with its justification.
6. Verdict.

**Success criteria.** The port is worth pursuing only if it meets every one of these; otherwise the report says
which criterion failed and why:

- **Performance:** at least 2× faster on search p95 or on perceived latency.
- **Footprint:** at most 50% of the RSS.
- **Output parity:** full golden parity for rows, notes Markdown and query order.
- **UI/UX parity:** no Missing rows in the matrix; every Adapted or Better row justified; no scripted task needs
  more keystrokes than in Raycast.
- **Quality:** every gate passes.

## Risks

| Risk                                                         | Mitigation                                                                                          |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| json2md quirks are hard to match byte for byte               | goldens first; port `markdown.ts` test by test against them                                         |
| YAML key order or scalar typing differs between parsers      | parser chosen by golden results; recorded in an ADR                                                 |
| GPUI has no global hotkey or launcher-panel primitive        | `global-hotkey` crate plus a pop-up window kind; isolated in `main`, recorded in ADR 0004           |
| Raycast's process is opaque, so tier 3 is noisy              | same external harness for both apps; medians, IQR and caveats in the report                        |
| `merman` and tree-sitter grammars inflate the binary         | sizes broken out per feature; grammars limited to languages present in the notes                    |
| GPUI Kit API churn                                           | exact version pinned; upgrade only deliberately                                                      |
